# Engineering Decisions

I built a competitive-intelligence engine for pharma: it reads dense industry documents into a structured model of drugs, trials, and regulatory events, then runs a research agent that answers competitive questions from that corpus, reaching out to live regulatory data sources when the documents fall short, and citing every claim it makes. An offline evaluation harness measures all of it. This document isn't about how the system works. It's about how I made decisions while building it. Four principles ran through all of it.

## 1. Build the evidence before you act on it

I don't optimize, add complexity, or tune anything until I have a measurement that says it's worth doing. This sounds obvious and almost nobody does it, because building the measurement first is slower and less satisfying than building the thing.

The labeled answer set, the scorer, and the baseline reports all existed before I wrote a line of the retrieval system they were meant to judge. Until "is this better?" is a question I can answer with a number, every improvement is a guess.

That ordering paid off directly. The retrieval system has two parts, a reliable baseline and a more sophisticated layer on top, and the obvious story is "the layer helps." Because I'd built the baseline and its evaluation first, I didn't have to assume that story, I could test it as a difference against the baseline. The evaluation showed a real gain, so the layer's value became a number I could defend instead of a hope. I'd also written down in advance that "it adds nothing" would be an acceptable result, because if you only build things you've already decided are good, you can't learn anything from them.

The same bar held when the system grew teeth. The agent can reach past the documents to live external data when the corpus comes up short, and live calls are the enemy of trustworthy measurement: they change under you, need credentials, and fail for reasons that have nothing to do with your code. So before I trusted a single live result, I recorded real responses once and replayed them through the same code path, so the evaluation runs identically every time, with no network and no keys. The point was never to avoid the network. It was that a measurement you can't reproduce isn't evidence, it's an anecdote, and that bar doesn't relax just because the thing you're measuring got harder to pin down.

## 2. Refuse knobs you can't justify

Every tunable parameter is a promise that you can set it correctly. If your evidence can't tell you the right setting, the knob isn't sophistication, it's a system that looks tuned while it's guessing. My rule: if the data can't resolve a parameter, it doesn't go in, and the limitation gets reported instead of hidden.

The clearest case prevented a misleading number. Combining two retrieval methods usually calls for a tunable weight controlling how much each counts. My evaluation set had nine scored queries, far too few to set that weight without fitting it to noise, so any value would have looked principled and meant nothing. I used a weighting-free method instead and said why.

A second knob justified the rule even more directly, because the data proved it was never needed. I'd deferred a similarity threshold to tune later, but the measurements came back bimodal, a clean match or no match, with no middle ground for a threshold to act on. The knob I'd been prepared to agonize over was inert, so I reported it as inert instead of inventing a calibration. A later fix wanted a fixed slot count I also couldn't justify, and I refused that one too.

The same instinct applied to a metric. I had open-ended fields like "therapeutic area" I could have scored for accuracy, but there's no standard taxonomy for them, so scoring them would mean inventing one and grading the system against my own invention. I reported those fields descriptively instead of turning them into a number that looked rigorous and measured nothing.

A parameter isn't the only thing that asks to be justified. A retry, a fallback wrapper, an extra state in a state machine, an abstraction layer over a single model provider: each is a degree of freedom, and each makes the same demand a knob does. When I gave the agent the ability to call external tools, the tempting move was to build machinery around failure, retry logic, a typed failure result threaded through the system, a new terminal state for each way a call could go wrong. I had no evidence any of that complexity was earning its place, so I didn't build it. A tool call that fails fails loudly, and I left it that way deliberately: I know exactly what graceful degradation would cost to add and what it would buy, and until the system is doing enough for that tradeoff to matter, the machinery stays on the shelf. Complexity is a knob too, and the question is the same: what does the evidence say I need?

## 3. Keep control where it can be tested

Every system has parts you can verify and parts you can only trust. The discipline is to know which is which, shrink the untrustworthy part to the smallest job that genuinely needs it, and draw a hard, testable line around it, so that when something breaks you can tell which side it broke on. The failure mode is the opposite: letting an untestable component quietly own decisions you could have verified, until you can't tell whether a bad outcome came from bad judgment or bad plumbing.

The component I couldn't test was the model itself. A language model is good at judgment and unreliable at bookkeeping, so I gave mine only the judgment calls, what to look for, whether the evidence in hand is enough, and how to phrase the answer, and kept everything around them in code I could run and measure. The loop those calls sit inside, the rule that ends it, the decision to reach for an external source, the link tying every claim back to its evidence: all code. The model never sees a document's identity and never declares itself finished. One common version of this kind of system hands the model the wheel and lets it manage its own loop and sources; I decided the opposite, because a control flow I've written is something I can trust to behave the same way twice, and a model improvising one is something I can only hope about.

Drawing the line there bought me more than reliability, it bought me legible failure. When the agent did something wrong, I could ask whether the model's judgment was bad or whether the code around it was, and those are different bugs with different fixes. A system where judgment and control are tangled together can't answer that question, so every failure becomes a guess. Narrowing the untestable part didn't make the system less capable. It made it something I could debug.

## 4. Localize before you solve

A bad aggregate number is almost never bad everywhere. Before I fix a low score, I break it down to find where the failure actually lives, because the fix for a localized problem is nothing like the fix for a diffuse one, and most improvements aimed at an average miss the real cause.

One extraction score, for regulatory events, came back around 0.41, low enough to look like a broken component. I traced it instead of treating it as general weakness. The misses weren't spread across the corpus; they concentrated in one pattern, where the model read the status cells of a particular kind of table as a different category of fact. Everywhere else it performed fine. So 0.41 wasn't a grade on the component, it was a diagnosis of one failure mode, and that told me the fix was narrow rather than a general overhaul.

The clearest payoff came on retrieval, where the diagnosis led straight to an architectural decision. Broken down by question type, the baseline was strong on direct lookups and weak on questions that gather scattered facts from across a document. That split was the whole signal: the weakness sat exactly where a structured, fact-level layer should help, since structured facts concentrate what long passages dilute. So I built that layer to target those questions, and the follow-up evaluation closed the loop, clear gains where the baseline was worst and little change where it was already strong. The improvement showed up precisely where localization said it would.

And sometimes localizing tells you the honest move is to stop. I found one question where the agent gave a confident, well-cited answer to the question next to the one I'd asked, and reported itself satisfied. It hadn't retrieved a wrong fact; it had answered a different fact about the right subject and never noticed the gap. I traced it to a single seam: the step that decides whether the evidence is sufficient was testing whether the subject was present, not whether the specific thing I'd asked about was. The obvious fix was a prompt change, so I made one, and at the setting that matters it returned a byte-for-byte identical answer. That told me what I needed to know: the problem wasn't in the wording, it was structural, and no prompt tuning was going to reach it. So I did the harder thing. I characterized exactly where and why it fails, wrote it down as a known limitation, and left the real fix for a structural change I could justify, rather than papering over it with a tweak I'd already watched fail. A precisely understood failure you've chosen not to chase is worth more than a fix you can't defend.

## The thread

These aren't four habits, they're one: let evidence drive the decisions, especially at a scale where most signals are noise and the easy move is to trust intuition over measurement. Build the measurement first; refuse the complexity it can't support; keep the untestable parts boxed where you can reason about them; trace every number to where it comes from. The discipline isn't in the tools. It's in being honest about what you actually know, including when what you know is that something is broken and you've chosen, for now, to leave it as it is.
